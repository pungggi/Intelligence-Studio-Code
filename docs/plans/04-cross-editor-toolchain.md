# CoreCode Native Extension System — Cross-Editor Build Toolchain

> **Status**: Planning
> **Created**: 2026-03-28

---

## Goal

A developer writes one extension in Rust. One build command produces packages for three targets:

```
cargo corecode build --target all

  → dist/
      my-ext-0.1.0.ccext          CoreCode package
      my-ext-0.1.0.zip            Zed package
      my-ext-0.1.0.vsix           VS Code package
```

---

## Package formats

### CoreCode package (`.ccext`)

A ZIP archive containing:

```
my-ext-0.1.0.ccext  (ZIP)
  corecode.toml
  extension.wasm
  webview/
    panel.html       (optional)
    panel.js         (optional)
```

Installed by dragging into CoreCode or via the marketplace CLI.

### Zed package (`.zip`)

Zed's extension format. The toolchain generates a `Zed-compatible` layout:

```
my-ext/
  extension.toml                  ← generated from corecode.toml
  extension.wasm                  ← same binary (wasm32-wasi)
  languages/
    my-lang/
      highlights.scm              ← from grammar-provider#highlights-query output
      injections.scm              ← from grammar-provider#injections-query output
  grammars/
    my-lang.wasm                  ← from grammar-provider#grammar-wasm output
```

**Compatibility note:** The same WASM binary works in Zed only for interfaces that Zed's host
also implements. For the `language-provider` and `grammar-provider` interfaces, Zed's WIT
definitions and CoreCode's are kept aligned by design. For `webview-provider`, Zed does not
currently have a webview API — webview panels are stripped from the Zed package with a build
warning; the rest of the extension continues to work.

### VS Code package (`.vsix`)

VS Code does not have a WASM extension host. The toolchain generates a thin Node.js wrapper
that loads the WASM binary via Node.js's native WebAssembly support and bridges WIT calls
to VS Code API calls.

```
my-ext-0.1.0.vsix  (ZIP)
  package.json                   ← generated; activationEvents (inferred from WIT exports), engines.vscode
  dist/
    extension.js                 ← generated adapter (Node.js)
    extension.wasm               ← same binary
  webview/
    panel.html                   ← same HTML
    panel.js                     ← same JS
    corecode-bridge.js           ← VS Code variant (acquireVsCodeApi)
```

**`activationEvents` mapping:** The build tool infers `activationEvents` from the WIT exports
declared in the WASM binary and any explicit declarations in `corecode.toml`:
- `language-provider` export → `onLanguage:<lang>` for each language in `[languages]`
- `grammar-provider` export → `onLanguage:<lang>`
- `webview-provider` export → `onCommand:<ext-id>.openPanel` (if custom commands are declared)
- Explicit entries in `corecode.toml` `[activation]` section override the inferred list

## The VS Code adapter (`dist/extension.js`)

The adapter is generated per-extension by the build tool. It is a Node.js VS Code extension
that:

1. Loads `extension.wasm` via `WebAssembly.instantiate`
2. Provides the WIT import implementations using VS Code APIs
3. Calls the WIT export functions from VS Code provider registration callbacks

Conceptual structure (generated, not hand-written):

```js
// dist/extension.js — GENERATED by cargo-corecode
import * as vscode from 'vscode';
import { instantiate } from './wit-bindgen-runtime.js';
import { readFileSync } from 'node:fs';

let ext;

export async function activate(context) {
  const wasm = readFileSync(context.extensionPath + '/dist/extension.wasm');
  ext = await instantiate(wasm, {
    // WIT imports implemented with vscode APIs
    workspace: {
      readFile: async (path) => {
        if (!vscode.workspace.workspaceFolders?.length) {
          throw new Error('No workspace folder open');
        }
        const uri = vscode.Uri.joinPath(
          vscode.workspace.workspaceFolders[0].uri, path
        );
        return new TextDecoder().decode(
          await vscode.workspace.fs.readFile(uri)
        );
      },
      getConfig: (key) => {
        const parts = key.split('.');
        const section = parts.slice(0, -1).join('.');
        const item = parts[parts.length - 1];
        // Preserve native types: booleans, numbers, strings, objects.
        // Only coerce to string for the WIT string return type.
        const val = vscode.workspace.getConfiguration(section).get(item);
        if (val === undefined || val === null) return '';
        if (typeof val === 'object') return JSON.stringify(val);
        return String(val);
      },
      // ... all workspace imports ...
    },
    ui: {
      log: (channel, msg) => {
        channels[channel] ??= vscode.window.createOutputChannel(channel);
        channels[channel].appendLine(msg);
      },
      showMessage: (level, msg) => {
        const fn = { info: 'showInformationMessage', warning: 'showWarningMessage',
                     error: 'showErrorMessage' }[level];
        vscode.window[fn]?.(msg);
      },
      setStatus: (id, text, tooltip) => { /* statusBarItem management */ },
    },
    webviewHost: {
      openPanel: (panelId, title, column) => {
        const panel = vscode.window.createWebviewPanel(
          panelId, title, column,
          { enableScripts: true, retainContextWhenHidden: true }
        );
        // Inject VS Code variant of corecode-bridge.js
        // state parameter: serialized panel state for restore, or null for new panels.
        // The template is embedded in the WASM binary via include_str!/include_bytes!
        // or loaded from a sidecar asset file in the extension directory.
        const html = ext['webview-provider'].getHtml(panelId, null /* state */);
        panel.webview.html = injectVsCodeBridge(html, panel.webview);
        panel.webview.onDidReceiveMessage(msg => {
          const response = ext['webview-provider'].onMessage(panelId, JSON.stringify(msg));
          if (response) panel.webview.postMessage(JSON.parse(response));
        });
        panel.onDidDispose(() => ext['webview-provider'].onClose(panelId));
        panels[panelId] = panel;
      },
      postToWebview: (panelId, json) => {
        panels[panelId]?.webview.postMessage(JSON.parse(json));
      },
      closePanel: (panelId) => {
        panels[panelId]?.dispose();
        delete panels[panelId];
      },
    },
    http: {
      fetch: async (req) => { /* Node.js fetch → response */ },
    },
  });

  await ext.lifecycle.activate();

  // Register providers based on what the WASM exports
  if (ext['language-provider']) {
    // Register only for languages declared in corecode.toml [languages],
    // not '*', to avoid incorrect triggers and unnecessary provider calls.
    const languages = manifest.languages ?? ['*'];
    for (const lang of languages) {
      context.subscriptions.push(
        vscode.languages.registerCompletionItemProvider(lang, {
          provideCompletionItems(doc, pos, _token, ctx) {
            try {
              const items = ext['language-provider'].completions(
                doc.uri.toString(),
                { line: pos.line, character: pos.character },
                ctx.triggerCharacter ?? null,
              );
              return items.map(toVscodeCompletion);
            } catch (e) {
              channels['corecode']?.appendLine(`completions error: ${e}`);
              return []; // safe fallback
            }
          }
        })
      );
    }
    // ... hover, diagnostics, format, definition, references, rename,
    //     code-actions, workspace-symbols, folding-ranges ...
  }
}

export async function deactivate() {
  await ext?.lifecycle.deactivate();
}
```

## Completion item mapping (`toVscodeCompletion`)

The adapter maps WIT `CompletionItem` fields to VS Code `CompletionItem`:

| WIT field       | VS Code field                 | Notes |
|:----------------|:------------------------------|:------|
| `label`         | `label`                       | Required |
| `kind`          | `kind` → `CompletionItemKind` | Map enum; unknown → `Text` |
| `detail`        | `detail`                      | Optional |
| `documentation` | `documentation`               | Optional; rendered as markdown |
| `insert_text`   | `insertText`                  | Optional; if absent, uses `label` |
| `filter_text`   | `filterText`                  | Optional |

VS Code-specific fields (`sortText`, `preselect`, `commitCharacters`, `additionalTextEdits`)
are omitted by the adapter — extensions that need them should use the Node.js host directly.

## Error handling policy

| Call site | On error | User-visible? |
|:----------|:---------|:--------------|
| `activate()` | Log full error to output channel + `showErrorMessage` | Yes |
| Provider calls (`completions`, `hover`, etc.) | Log + return empty/null | No (silent fallback) |
| `webview-provider.onMessage` | Log + optionally post error back to webview | No |
| WASM trap/panic | Log stack + `showErrorMessage` | Yes |

All external calls (`instantiate`, `ext[...]` calls, webview `postMessage`) must be wrapped
in `try/catch`. Errors include the WASM extension id and function name for traceability.

## The VS Code webview bridge (`corecode-bridge.js` — VS Code variant)

Swapped in at build time for the VS Code target:

```js
// corecode-bridge.js — VS Code variant (generated into .vsix)
const vscodeApi = acquireVsCodeApi();
window.coreCode = {
  postMessage(data) {
    vscodeApi.postMessage(data);
  }
};
window.addEventListener('message', (event) => {
  // VS Code delivers extension messages here
  // No change needed — same event model
});
```

Extension's `panel.js` is unchanged. Only this file differs between targets.

## cargo-corecode CLI

The toolchain is implemented as a Cargo subcommand (`cargo-corecode`), published as a standalone
binary. It is not a Cargo plugin inside the extension source; it's an external tool.

```
cargo corecode new my-ext           # scaffold new extension project
cargo corecode build                # build for CoreCode only
cargo corecode build --target zed   # build CoreCode + Zed packages
cargo corecode build --target all   # build all three packages
cargo corecode check                # WIT compatibility check (no compile)
cargo corecode publish              # publish to CoreCode marketplace
```

### `cargo corecode check`

Validates that the WASM binary's exports are compatible with the current WIT spec and with
the target editor's API subset. Reports which features will be silently dropped for each target.

Example output:
```
CoreCode   ✓ all interfaces supported
Zed        ✓ language-provider, grammar-provider
           ⚠ webview-provider — not supported in Zed (will be excluded)
VS Code    ✓ language-provider, grammar-provider, webview-provider
           ⚠ http#fetch — requires networkFetch capability in package.json
```

## Keeping WIT definitions aligned with Zed

The CoreCode WIT types are versioned. For each release, the team publishes a compatibility
matrix in `wit/compat/` showing which CoreCode WIT version maps to which Zed API version.
When Zed updates its WIT interface, the build tool's Zed backend is updated to match; the
extension developer recompiles with `cargo corecode build --target zed` and the adapter
handles translation.

Extensions that use only stable interfaces (`language-provider`, `grammar-provider`,
`workspace`, `ui`) are expected to remain Zed-compatible across minor versions without
any changes to the extension source.
